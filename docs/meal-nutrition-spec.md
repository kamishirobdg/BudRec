# 食事・栄養記録 仕様書（ドラフト）

最終更新: 2026-10-08 / 状態: **段階 1〜3・5 と段階 4 の一部を実装済み（v2.5.1、実機未確認）**。成分表の同梱は未決（§9）

家計簿として登録しているレシート・ネットスーパーの明細を土台に、食事の写真から
「何を・誰が・どれだけ食べたか」と栄養を記録する。家計簿と同じアプリで完結させ、
記録の手間は「撮るだけ」を崩さない。

---

## 1. 決定事項

| 項目 | 決定 |
|---|---|
| 栄養値の精度 | チェーン店メニュー・パッケージ商品は **Google 検索 grounding を必ず使う**（公式の栄養表示を引く） |
| 記録する栄養素 | **取れるものはすべて保存する。** どれを表示するかは後から、ユーザーごとに選べるようにする |
| 記録範囲 | 外食・コンビニ・自炊のすべて。毎食撮影する運用を前提にする |
| 自炊の判別 | 撮影された食材は**登録済みのレシート・明細のどこかに必ず登場する**前提で、購入履歴から候補を絞る |
| 誰が食べたか | 撮影→レシート撮影の流れで、写真の料理とレシートの品目を突き合わせる。一品で完結しない食事（焼肉・寿司など）は**半分ずつを初期値**にする |
| 確認の挟み方 | **判別に困る場合だけ確認する。** 一人前と自明に分かる場合などは確認せず自動で確定し、**後からいつでも変更できる** |
| 好みの学習 | 手修正の履歴を蓄積し、次回の推定に使う |
| 無料枠を超えた場合 | **ためておき、枠のリセット後に自動で処理し直す**（レシート OCR にも同じ仕組みを使う） |
| 支出行の ID | 月次シートに M 列 `entry_id` を足す（§3.1） |
| 撮影の種類 | **選ばせない**（2026-10-08）。1 回の呼び出しでレシートと料理・食品に振り分けて読む（両方写っていれば両方）。呼び出し回数は増えない |
| 初回のユーザー名 | 登録済みの名前から選べる。端末 ID（ANDROID_ID。同じ署名なら再インストールしても同じ）で、前に使っていた名前を自動で選んでおく。別の端末が 30 日以内に使った名前を選ぶと確認する（§3.8） |
| 食品データ | `_foods` に品目・メニューごとの栄養を持ち、何度出てきても検索は 1 回で済ませる。価格は記録するだけ（使い道が決まるまで）。空き時間に購入回数の多い順に全品目を調べる（1 日 30 件まで）。180 日で調べ直し、画面の「栄養を調べ直す」でいつでも調べ直せる（§3.7） |
| 在庫 | 保存の種類（冷蔵 / 冷凍 / 常温）と品目ごとの日持ちの日数を持つ。日持ちを過ぎたら操作しなくても在庫から外れる。食べた量だけ残りを減らし、ほぼ無くなったら「食べきりましたか？」と聞く。個数で数えるものは個数で数える（§5.3） |
| 見分けられない食材 | 予測で記録する。同じ種類の候補が複数あって見分けられないときだけ、候補を選択肢にして「要確認」で後から選んでもらう |
| 写真 | レシート・食事とも**端末内に残す**（§3.5）。二人でした食事の写真とそのレシートは、**共有用シートに一時的に置いて二人で見られる**ようにし、編集・保存から 7 日または共有から 14 日で消す（§3.5.1）。Google Drive は使わない |
| GPS | **棚上げ**（店舗特定に Google Places API の課金が要るため）。HANDOFF の「将来やりたいこと」に記録済み |

## 2. 段階

| 段階 | 内容 | 前提 |
|---|---|---|
| 1 | 支出行の `entry_id`、レシート・Gmail 明細の**品目を構造化して保存**、レシート写真を端末内に残す | なし |
| 2 | 食事写真の記録、外食・コンビニの判別、レシートとのひも付け、誰が食べたかの割り振り、grounding による栄養推定、無料枠超過時のバッチ再処理 | 1 |
| 3 | 自炊の判別（購入食材からの候補絞り込み・量の推定・食材の残量管理） | 1, 2 |
| 4 | 手修正の履歴を使った初期値の改善（分け方・量） | 2 |
| 5 | 表示（日・週・月の集計、ユーザーごとの表示項目の選択） | 2 |

段階 1 だけでも家計簿側に価値がある（品目単位の検索・集計ができる）。

## 3. データモデル

既存の方針どおり Google スプレッドシートを DB として使う。月次シート（`YYYY-MM`）の
命名規則にかからないよう、新しいシートは先頭を `_` にする。行数を抑えるため月ごとに分ける。

### 3.1 支出行の ID（既存シートの変更）

品目・食事から支出行を参照するために、支出行に安定した ID が要る。現状は
`sheetName + rowIndex`（論理削除なので基本は不変だが、ヘッダー差し込み時にずれうる）か、
「前回の登録」と同じ内容キー（シート名・日時・店名・金額）しか無い。

**決定（2026-10-07）: 月次シートに M 列 `entry_id`（UUID）を足す。**

- 新規行から付与し、既存行は空のまま（品目・食事から参照されるのは新規行だけなので困らない）。
- 読み出しと追記の範囲を `A:L` → `A:M` に広げる。新しく作る月次シートのヘッダーには `entry_id` を足す
  （既存の月次シートの M1 は空のまま）。
- **編集（`updateRow`）は今までどおり `A:L` だけを書き、M 列には触らない。** 画面側が ID を持たずに
  書き戻しても ID が消えない。そのため未送信キューの列の重なり判定は変更不要。
- 固定費のコピー（月初の自動作成）は、コピー先の行に新しい ID を振る。
- 不採用: 列を増やさず内容キー（シート名・日時・店名・金額）で参照する案。編集で日時・金額を
  直すと参照が切れるため。

### 3.2 `_items_YYYY-MM`（購入品目）

レシート OCR・Gmail 取り込み時に、支出行と同時に書く。

| 列 | 内容 |
|---|---|
| item_id | UUID |
| entry_id | 支出行の ID |
| purchased_at | 購入日時（支出行と同じ形式 `YYYY/MM/DD HH:MM:SS`） |
| user | 購入者（支出行の user と同じ） |
| store | 店名 |
| name_raw | レシートの表記そのまま（`ｺｸｻﾝﾌﾞﾀｺﾏ` など） |
| name | 正規化した品名（`国産豚こま切れ肉`） |
| quantity / unit | 数量と単位（`300` / `g`。不明なら空） |
| amount | 金額 |
| food_kind | `ingredient`（生鮮・食材）/ `packaged`（そのまま食べる商品）/ `non_food`（日用品など） |
| storage | `chilled`（冷蔵）/ `frozen`（冷凍・アイス）/ `ambient`（常温） |
| shelf_days | 買ってから食べきるまでの目安の日数（品目ごとの推定。肉 3、卵 14、冷凍食品 60 など） |
| pieces | 入り数（アイス 6 本入りなら 6）。個数で数えないものは空 |
| remaining | 残りの割合（0〜1。初期値 1） |
| remaining_pieces | 残りの個数（個数で数えるものだけ） |
| status | `in_stock`（在庫）/ `confirm`（食べきったか確認待ち）/ `used_up`（食べきった） |
| food_id | 食品データ（§3.7）と対応付けたら入る（今は空。品名から引く） |
| updated_at | 在庫の状態を最後に書き換えた日時 |

列は `A:S`。在庫としての扱いは §5.3。

- 正規化（半角カナの展開・略称の解決・分類）は OCR と同じ Gemini 呼び出しの中で行う。
- `non_food` は食事の候補から外す。
- 既存のメモ欄（`品名:価格, …`）は従来どおり残す（家計簿側の表示を変えない）。

### 3.3 `_meals_YYYY-MM`（食事）

**1 行 = 1 人 × 1 品。** 二人で分けた料理は 2 行になる。

| 列 | 内容 |
|---|---|
| meal_id | 1 回の食事の ID（同じ写真・同じ食事の行で共通） |
| dish_id | 1 品の ID（二人で分けた品は 2 行で共通） |
| eaten_at | 食べた日時（写真の撮影日時） |
| user | 食べた人 |
| kind | `eat_out`（外食）/ `packaged`（コンビニ等の商品）/ `home`（自炊） |
| store | 店名（ひも付いたレシートの店名。自炊は空） |
| dish | 料理名 |
| portion | その人が食べた割合（1 品全体に対して 0〜1。半分ずつなら 0.5） |
| nutrients | 栄養素の JSON（§4）。**その人が食べた分の値** |
| nutrient_source | `grounding` / `food_table`（成分表）/ `estimate`（モデルの推定） |
| confidence | 推定の確からしさ（`high` / `medium` / `low`） |
| entry_id | ひも付いた支出行（外食・コンビニ） |
| item_refs | 使った購入品目と量の JSON（自炊。`[{item_id, used_ratio}]`） |
| status | `estimated`（確定）/ `needs_review`（確認が要る）/ `edited`（手修正済み） |
| assigned_by | `auto` / `manual` |
| photo_refs | 食事写真の保存先の JSON 配列（§3.5）。1 回の食事に複数枚付けられる。撮った端末でだけ開ける |
| rev | 同時編集の検出用（§3.5.2）。保存のたびに 1 増える |
| sources | grounding で参照したページの URL の JSON 配列 |
| updated_by / updated_at | 最後に保存した人・日時 |
| deleted | 論理削除（`TRUE`）。行番号をずらさないため行は消さない |
| choices | 在庫のうち見分けられなかった候補の JSON（`[{itemId, name, store, bought}]`）。選ばれたら空にする |

推定待ち（無料枠切れ）の食事は、この表には書かずに端末の画像キューで `deferred` として待たせる
（推定が済んでから行を作る）。食事の一覧には「推定待ち N 件」とだけ出す。

### 3.4 `_meal_corrections`（手修正の履歴）

段階 4 のための記録。手修正のたびに 1 行追記する。

| 列 | 内容 |
|---|---|
| corrected_at | 修正日時 |
| meal_id / dish_id | 対象 |
| field | `user` / `portion` / `dish` / `amount`（量） |
| before / after | 修正前後の値 |
| context | 店名・料理の種類など（推定時に似た状況を引くため） |

### 3.5 写真の保存

**方針（2026-10-07）: レシート・食事の写真を処理後も端末内に残す。**（従来はレシート画像を登録後に削除していた）

- 保存先は `<documentDirectory>/photos/receipts/` と `<documentDirectory>/photos/meals/`。
  食事の行は `photo_ref` 列（保存先を表す文字列）で参照する。レシートの写真は、端末内の
  対応表（`photo-index.json`: `entry_id` → `photo_ref`）で支出行とひも付ける。写真が端末内にしか
  無い間は、共有シートに端末のパスを書いても相手には意味が無いため。
- `photo_ref` は `local:photos/meals/xxx.jpg` の形にしておき、保存先の種類を足せるようにする。
- 写真は撮った端末にしか無い。ただし二人でした食事の写真とそのレシートは、一定期間だけ共有用シート経由で
  相手の端末からも見られる（§3.5.1）。
- 保存期間を設定できるようにする（既定は無期限。端末の容量が気になれば日数で古いものを消す）。

#### 3.5.1 二人で見る写真をスプレッドシート経由で共有する（段階 2）

**方針（2026-10-07）: 二人でした食事の写真と、それにひも付くレシートの写真だけを、スプレッドシートの
共有用シートに一時的に置く。二人とも写真を見てレコードを編集でき、用が済んだらシートから消す。**
それ以外の写真は端末内のまま。

Google Drive に置く案は不採用。相手が作ったファイルを読むには制限付きスコープ `drive.readonly` が要り、
Drive API の有効化・同意画面へのスコープ追加・二人の再ログインが必要になるため。シート経由なら
今の `spreadsheets` スコープだけで済み、設定作業も再ログインも要らない。

- **Sheets API には画像を貼る操作が無い**（`=IMAGE()` は公開 URL が要るので使わない）。画像を
  base64 の文字列にしてセルに入れ、相手の端末で読み出して画像に戻す。
- 対象: 食べた人が二人にまたがる食事（`_meals` で同じ `meal_id` に二人の行がある）の写真と、
  その食事に `entry_id` でひも付くレシートの写真。対象になった時点で書き込む。
  **1 回の食事に複数枚の写真を付けられる。** 共有中の食事の数にも上限を設けない
  （休日に外食が続いても、それぞれの食事の写真を並行して共有できる）。
- 縮小（`expo-image-manipulator`）は種類ごとに変える。圧縮しすぎると相手の端末で見にくくなるため:
  - 食事: 長辺 1600px・JPEG 品質 0.75。1 枚 200〜350KB
  - レシート: **横幅を 1000px に揃える**（長辺で揃えると、長いレシートは横幅が 300px ほどになり文字が潰れる）・
    品質 0.75。長さ次第で 250〜500KB
  - **1 セル 5 万文字の上限**があるので、base64 を 4 万文字ずつに分けて横に並べる（食事 6〜10 セル、レシート 8〜15 セル）。
- **見る写真の優先順**:
  1. 撮った本人の端末では、端末に残っている**元の写真**を表示する（縮小版は使わない）
  2. 相手の端末では、共有用シートから読んだ縮小版を表示する。読んだものは端末に保存し
     （`photos/shared/`）、共有用シートから消えた後も見られる（端末側の保存期間の設定に従う）
- 共有用シート `_shared_photos`（**非表示シート**にする。ブラウザで開いても文字の羅列が目に入らない）:

  | 列 | 内容 |
  |---|---|
  | photo_id | UUID |
  | meal_id / entry_id | ひも付く食事・支出行 |
  | kind | `meal` / `receipt` |
  | shared_by / shared_at | 共有した人・日時 |
  | settled_at | 「必要な編集と保存」が済んだ日時（下記）。済んでいなければ空 |
  | chunk_count | 分割数 |
  | chunk_1 〜 | base64 を分割したもの |

- **読み出しは開いたときにその 1 行だけ**（`A:H` の目録は軽いので一覧用に読み、画像本体は必要なときに読む）。
  読んだ画像は端末にキャッシュする。
- **消すタイミング（どちらか早い方）**:
  1. どちらかの端末で、その食事の**必要な編集と保存**が済んでから 7 日経った
  2. 共有してから 14 日経った
  - 「必要な編集と保存」= 食事の編集画面で保存したこと（変更なしで「確定」を押した場合も含む）。
    保存した時点で `settled_at` を記録する。**どちらか一方の端末で済めば、両方の端末で見る必要は無い。**
  - 二人で同じ画面を見ながら片方の端末で入力する使い方を想定している。
  - 保存し直したら `settled_at` を更新する（7 日はそこから数え直す）。
  - 期限を過ぎた行は、どちらかの端末がアプリを開いたときに消す。
- **消し方は行のクリア（値を空にする）**。行削除（`deleteDimension`）は行番号がずれるため、
  二人が同時に消そうとすると別の行を消しかねない。
- **追記は `insertDataOption: OVERWRITE`**。`INSERT_ROWS` だと、空にした行の位置に行が差し込まれて
  下の行の行番号がずれる。`OVERWRITE` なら表の直後の空行（空にした行）を使い回すので、空行も溜まらない。
  - 二人がほぼ同時に共有すると、同じ空行に書いてしまい片方の写真が消える可能性がある（まれなので許容）。
  - 読み出すときは行の photo_id を確かめ、別の写真に使い回されていたら読まない。
- 消すのは共有用のコピーだけ。撮った人の端末には元の写真が残る。
- 重さの見積もり: 1 枚の書き込みは数秒。20 枚が同時に共有中でも 6〜8MB 程度。アプリ側は範囲を絞って
  読むので他の画面は遅くならない。ブラウザでスプレッドシートを開くときの待ち時間は増える。
  **3〜5 枚で書き込み・表示が重いと実機で分かった場合は、方式を見直す。**
- 二人の名前（代理入力の相手の候補）は、各端末がサインイン時に `_users` シートへ自分のユーザー名を
  登録する形にする。代理入力の相手を「シートに記録があるか」に頼らず選べるようになる
  （HANDOFF の既知の制限が解消する）。

### 3.5.2 同時編集の検出と、元に戻す（段階 2）

**方針（2026-10-07）: 二人が同じレコードを編集した場合、後から保存しようとした側に警告を出して選ばせる。
間違えたときのために、上書きされた内容に戻せるようにする。**

- 対象は支出行と食事の行（どちらも二人とも編集できる）。
- 支出行に N 列 `rev`（更新のたびに 1 増やす整数）と O 列 `writer`（最後に書いた端末の ID）、`_meals` に `rev` 列を足す。
  支出行は、rev が違っても**最後に書いたのが自分の端末なら競合にしない**（自分の直前の書き込み・古いキャッシュ・
  届いたのに応答が無かった送り直しを競合扱いにしないため）。
  画面に読み込んだときの `rev` を覚えておき、保存の直前にシートの `rev` を読み直して比べる。
  - 同じ → そのまま保存し、`rev` を 1 増やす。
  - 違う（相手が先に保存した）→ 警告を出し、「相手の内容を残す」「自分の内容で上書きする」を選ばせる。
    相手の内容（変わった項目）を並べて見せる。
- **上書きされる直前の内容は `_history` シートに残す**（シート名・行・`rev`・保存した人・日時・行の内容の JSON）。
  レコードの編集画面に「以前の内容に戻す」を置き、`_history` から選んで戻せる（戻す操作も 1 回の保存として扱う）。
- 読み直しから書き込みまでの間（1 往復ぶん）に相手が保存した場合は検出できない。Sheets API に
  条件付き書き込みが無いため許容する（`_history` から戻せる）。
- 未送信キューから後で流れる書き込みも同じく比べる。食い違ったら送らずに止め、設定画面の
  「未送信の変更」に「競合」として出して選ばせる（裏で勝手に上書きしない）。
- 段階 1 では `rev` 列はまだ足さない（M 列 `entry_id` だけ）。段階 2 で `rev` と競合検出をまとめて入れる。

### 3.7 `_foods`（食品データ）（v2.1.0）

品目・メニューごとに栄養を持ち、同じ食品が何度出てきても検索は最初の 1 回で済ませる。

| 列 | 内容 |
|---|---|
| food_id / key | ID と引くための鍵（品名。外食のメニューは `チェーン名|メニュー名`。空白と大小文字だけ揃える） |
| name / chain / kind | 品名・チェーン名・種類 |
| storage / shelf_days / pieces / content | 保存・日持ち・入り数・内容量（品目の最新の値） |
| nutrients / basis | 栄養の JSON と単位（`package` = 1 個・1 パック・一人前あたり / `per100g`） |
| source / sources / fetched_at | `grounding`（公式表示）/ `estimate`、参照 URL、調べた日時 |
| purchase_count / last_price / prices | 購入回数・最近の価格・価格の履歴（**記録するだけ**。使い道が決まるまで画面では使わない） |
| status | `pending`（未調査）/ `done` / `failed` |

- レシート・メールの品目を登録したら、購入回数と価格を記録する（`FoodService.recordPurchases`）。
- 栄養が要るときはまずここを引き、無いものだけ grounding で調べてここに足す。
- **空き時間に、未調査の品目を購入回数の多い順に調べる**（OCR の待ちが無いとき・アプリ起動時・定期実行時。
  1 回 5 品・1 日 30 品まで。二人分の買い物なら全品目を調べても量は問題にならない）。
- 調べてから 180 日経ったら調べ直す。在庫の画面・食事の編集画面の「栄養を調べ直す」でいつでも調べ直せる。
- 二人の端末が同じ品目を同時に足すと同じ鍵の行が 2 行できうる（読むときは後の行を使う。害は無い）。

#### 3.7.1 `_menus` と店のオリジナル商品（v2.7.0）

- **外食のメニュー（店の分かる eat_out）は `_menus` に分ける**（列は `_foods` と同じ）。チェーン店の全メニューで
  数千行あり、`_foods` に置くとレシートを 1 枚登録するたびに数 MB を読むため。`_menus` は外食の栄養を引くときだけ読み、
  端末（`menus-cache.json`）に 24 時間置いて使い回す。書き込むと端末の分は捨てる。店の分からない外食（レシートと
  結び付かない料理）は品名だけの鍵で引くので `_foods` に置く。
- **店のオリジナル商品**（コンビニ・スーパーの PB、店内調理の弁当・総菜・パン、ファミチキなど）は、OCR が品目ごとに
  `ownBrand` を返し、`スーパー・コンビニのチェーン名|品名` の鍵で `_foods` に入れる（別の店の同じ名前の商品と混ざらない）。
  チェーン名は店名から出す（`ChainService.retailChainOf`。セブン-イレブン・ファミリーマート・ローソンなどは別名の表で、
  表に無い店は末尾の「〇〇店」を除いた店名）。引くときは「チェーン名|品名」→「品名」の順に見て、新しい栄養がある方を使う。
- 既存の 427 品目は 2026-10-08 に Claude Code が判定して付け直した（189 件がオリジナル商品）。

## 4. 栄養素の持ち方

- **取れた栄養素はすべて保存する。** 表示の取捨選択は保存とは切り離す（§3.6）。
- キーは日本食品標準成分表の成分識別子（INFOODS タグ。`ENERC_KCAL`、`PROT-`、`FAT-`、
  `CHOAVL`、`FIB-`、`NACL_EQ` など）に揃える。grounding で得た公式表示も同じキーへ対応付ける
  （「熱量」→ `ENERC_KCAL`、「食塩相当量」→ `NACL_EQ` など）。
- **値が無い項目は `null`。0 とは区別する。** 合計を出すとき、`null` を 0 として足さない。
  日ごとの合計には「一部の食事でこの項目が不明」の印を付ける。
- 出どころごとの目安:
  - 成分表（生鮮食材）: 50 項目前後（ビタミン・ミネラルまで）
  - grounding（チェーン店メニュー・パッケージ商品）: 公式表示にある 5〜7 項目程度
  - モデルの推定: 主要項目のみ。`confidence` は `low` 以下にする

### 4.1 日本食品標準成分表

- 文部科学省の公開データ（約 2,500 食品）を JSON に変換してアプリに同梱する（数 MB 以内の見込み）。
- 利用条件（出典の表示など）は実装前に確認する（§9）。

## 5. 処理の流れ

撮影の種類は選ばせない（2026-10-08）。撮った写真は `OcrWorker`（裏で 1 枚ずつ処理）に積み、
**1 回の呼び出しでレシートと料理・食品に振り分けて読む**（`GeminiMeal.analyzePhoto`）。
両方写っていれば両方として処理し、同じ写真のレシートにそのまま食事をひも付ける。
振り分けの結果（ID を振った支出行・料理・食事の ID・在庫の候補）は画像の状態ファイルに残してから書き始め、
途中でアプリが終了されても Gemini を呼び直さず、書けていないものだけ続きから書く。

### 5.1 食事写真

1. 振り分けの呼び出しで、料理・食品ごとに次を返す: 料理名・種類（外食 / 商品 / 自炊）・一人前かどうか・
   取り分けか・判別の確からしさ・使った在庫と量・見分けられない候補（§5.3）。
2. ひも付け先を探す（外食・商品は §5.2、自炊は §5.3）。
3. 栄養を出す（§6）。
4. 誰が食べたかを決める（§5.4）。
5. 判別に困らなければ `estimated` で確定し、困れば `needs_review` にする（§5.5）。

### 5.2 外食・コンビニ（レシートとのひも付け）

- 食事写真とレシートを**撮影時刻の近さ**で突き合わせる（前後 3 時間以内を目安。レシートが先でも
  後でもよい）。食事写真を処理した時点で相手が無ければ、後からレシートが来たときに改めて突き合わせる。
- 写真の料理とレシートの品目を Gemini に対応付けさせる。対応が付いた品は、
  レシートの正式な品名と金額で grounding する。
- レシートが見つからない場合（撮り忘れ・現金で受け取らなかった等）は、写真だけで推定し
  `confidence` を下げる。

### 5.3 在庫と自炊（購入食材からの判別）（v2.1.0）

- **在庫** = 直近 6 か月に買った食品（`non_food` 以外）のうち、食べきっておらず、日持ちの範囲内のもの。
  日持ち = 品目ごとの推定日数（`shelf_days`）。ただし冷蔵は最低 3 日、冷凍・常温は最低 30 日残す。
  **日持ちを過ぎたら操作しなくても在庫から外れる**（書き込みはせず、読むときに判定する）。
  削除した支出行の品目は在庫にしない。
- 振り分けの呼び出しに在庫（最大 80 件。品名・店・買った日・保存・残り）を渡し、料理・食品ごとに
  **使った在庫と量**（個数で数えるものは個数、それ以外は残りに対する割合）を返させる。
  残りの量を上限にすることで量の推定を絞る。
- **見分けられない候補**（同じ種類が複数あって写真から見分けられない。例: 冷凍からあげが 2 種類）が
  あるときは、候補を `_meals` の `choices` に残して `needs_review` にする。食事の編集画面に
  「どれですか？」として並べ、選んでもらう（「どれでもない」も選べる）。**選ぶまで在庫の残りは減らさない。**
  見分けられるときは聞かずに予測で記録する。
- 記録したら使った分だけ残りを減らす（`InventoryService.consume`）。個数で数えるものは個数、それ以外は割合。
  **ほぼ無くなったら（個数 0、割合 10% 以下）**`status = confirm` にし、在庫の画面の先頭に
  「食べきりましたか？」として出す（「食べきった」「まだある」）。「食べきった」は在庫の画面からいつでも押せる。
- 在庫の画面は「食事」タブの「在庫」。冷蔵・冷凍・常温に分けて、残り・買った日・あと何日を出す。
- 調味料・油は写真に写らないので、料理の種類ごとの目安量を加える（例: 炒め物は油 大さじ 1）。

### 5.4 誰が食べたか

- 写真を撮った端末の利用者（代理入力中なら代理相手）を、既定の食べた人にする。
- 1 枚に複数の品が写っていて、一人前の品が人数分ある場合は、品ごとに割り振る。
  割り振りは手修正の履歴（§7）を参考に Gemini が推定する。
- 一品で完結しない食事（焼肉・寿司・鍋・大皿料理など）は、**二人で半分ずつ**を初期値にする。

### 5.5 確認を挟む条件

次のどれかに当たる場合だけ `needs_review` にして、撮影画面の「要確認」に出す。
それ以外は確認なしで確定する。

- 一人前の品が複数あり、誰の品か推定の確からしさが低い
- レシートの品目と写真の料理の対応が付かない品がある
- 自炊で、候補食材に当てはまらないものが主役の料理になっている
- 料理そのものを判別できない

一人前と自明に分かる品（定食・丼・ラーメン一杯など）を一人で撮った場合は確認しない。

### 5.6 後からの変更

食事の一覧から、どの行でも次を変更できる。変更した行は `status = edited`、`assigned_by = manual`
にし、§3.4 に履歴を残す。

- 食べた人・割合（半分ずつ → 7:3 など）
- 料理名（変えたら栄養を推定し直す）
- 量（自炊の使用量。変えたら `remaining` も戻して付け直す）
- 削除

## 6. 栄養の求め方

| 種類 | 方法 |
|---|---|
| チェーン店のメニュー | grounding（店名＋レシートの品名で公式の栄養表示を検索） |
| パッケージ商品（コンビニ等） | grounding（商品名で栄養成分表示を検索）。既定は 1 個まるごと食べた扱い |
| 自炊 | 使った食材ごとに成分表 × 推定量。調味料の目安量を加える |
| 上記で取れない場合 | モデルの推定（`nutrient_source = estimate`、`confidence = low`） |

### 6.1 grounding の技術的な注意（実装前に検証）

- Gemini API の Google 検索 grounding と、構造化出力（`responseSchema`）を同じ呼び出しで
  併用できるかはモデルによって異なる。使えない場合は 2 段階にする
  （1 回目: grounding で検索し出典付きの文章を得る → 2 回目: その文章を JSON に整える）。
- grounding の結果に出典 URL が付くので、食事の行に残しておく（誤りに気づいたとき確かめられるように）。
- grounding の無料枠は通常の呼び出しより小さい。毎食使うと 1 日に数回〜十数回になる。

## 7. 手修正の履歴を使った推定（段階 4）

- 機械学習のモデルは作らない。推定の指示文に、**似た状況の直近の修正履歴**を添える
  （同じ店・同じ料理の種類・同じ取り分け方を優先して最大 20 件程度）。
- 例: 「焼肉店では夫:妻 = 6:4 に直されることが多い」「サラダは妻に割り当て直されることが多い」。
- 修正の傾向は表示用にも集計できる（誰がどんな食事を好むか）。

## 8. 無料枠を超えた場合のバッチ再処理

レシート OCR と食事の推定の両方に適用する。

- Gemini の 429 応答に含まれる情報（`QuotaFailure` の対象、`RetryInfo` の待ち時間）で分類する。
  - **分単位の枠**: 指定の待ち時間だけ待ってその場で再送する。
  - **日単位の枠**: ジョブを `deferred` にし、再処理してよい時刻（`notBefore`）を記録する。
    `RetryInfo` に待ち時間があればそれを使い、無ければ次の米国太平洋時間 0 時
    （日本時間 16 時または 17 時）とする。**時刻はコードに決め打ちしない。**
- 推定待ちの食事は一覧に「未推定」として出す。レシートも「推定待ち」として要確認とは分けて出す。
- 再処理のきっかけ:
  - アプリが前面に来たとき、`notBefore` を過ぎたものをすぐ処理する。
  - Android の定期実行（WorkManager。`expo-background-task`）で、アプリを開かなくても処理する。
    **最短 15 分間隔で、正確な時刻には動かない**（スリープ中は数時間遅れることもある）。
- 今のモデル切り替え（429 で別モデルへ逃げる）は残す。全モデルが日単位の枠切れになったときに
  `deferred` にする。grounding の枠はモデルを替えても回復しない可能性があるので、別に判定する。

## 8.8 次に実装すること（2026-10-08 決定。2026-10-08〜09 に v2.1.1〜v2.3.0 で実装。実機未確認）

**実装メモ（v2.2.0〜v2.3.0）**
- 方式 A: 設定画面「食品データの一括調査」（`components/FoodResearchCard.tsx` / `services/FoodResearchService.ts`）。
  品目は月次シートのメモ欄（カテゴリ名に「食」を含む行だけ）と `_items` から集め、レジ袋・値引などは名前で外す。
  文面は Android の共有で送る。貼り付けはタブ区切りのほか Markdown の表も受け付ける（タブが空白に変わった表は、
  列がずれるので読まない）。前回の文面に載せたのに答えに無かった品目は、端末に覚えて 30 日は載せない
  （`failed` にはしない。答えが途中で切れただけでも空き時間の調査から永久に外れてしまうため）。前回の文面と無関係な
  表（方式 C の表など）を貼ったときは印を付けない。品名に「（内容量）」を付けて返されたら外して照合する。
  メモ欄の品目は entry_id の無い行（`_items` が無い頃のレシート）だけ数え、削除した行は数えない。
  外食のメニューは `チェーン名|品名` で入るので、「調べ済み」はチェーン名を問わず品名で判断する。
- 購入の記録は端末の中で 1 つずつ順に行う（未記録分の記録と OCR・Gmail の記録が重なって回数が消えないように）。
  既存の品目の書き換えだけ済んで新しい品目の追記に失敗したときは、新しい品目だけ残す。送り直しても通らない失敗
  （400 など）は残さない。
- 外食のメニューは、店名（「マクドナルド 船橋日大前店」）に含まれるチェーン名で `チェーン名|メニュー名` を引く
  （`FoodService.findMenu`）。品名はレシートの品名と写真から読んだ料理名の両方で試す。
- パッケージ画像: `_foods` の T 列 `image_url`（`-` = 見つからなかった）。参照ページは 5 品ぶんまとめて返るので、
  ページの題名と品名の近さ（2 文字ずつの一致率 0.3 以上）でどの品のページかを決める。空き時間の調査の後に
  1 回 5 品ずつ探す（`FoodImages.fillSomeImages`。AI の無料枠は使わない）。端末の `photos/foods/<food_id>.img` に保存
  （一時ファイルに落としてから移す。画像でなければ保存しない）。どのページも読めなかった品目は `-` にせず次の起動で探し直す。
- 外食のメニューを引くときは、店名に含まれるチェーン名を長い順にすべて試す（自動の調査は店名そのものをチェーン名として
  保存するので、「マクドナルド 船橋日大前店」と「マクドナルド」の両方がありうる）。チェーン名には別名の対応表
  （`FoodService.CHAIN_ALIASES`。「MOS BURGER」「KFC」など）があり、全角・空白・中黒の違いは無視して照合する（v2.3.2）。

### 8.8.1 食品データの一括調査（Web の AI を使う。方式 A と C を併用）

API の無料枠を使わずに、これまでのレシートから食品データ（§3.7）をまとめて整理・調査する。

- **材料:** 各月のシートのメモ欄（G 列。``品名:価格, …``。v1.9 より前のレシートはここにしか品目が無い）と
  ``_items_YYYY-MM``（v1.9 以降）。半角カナ・略称の品名も含めて、同じ品目をまとめてから調べる。
- **方式 C（今回の一括調査は Claude Code が行う）:** Claude Code が Google ドライブ連携でスプレッドシート
  （``Bud-Rec``、ID は ``.env`` の ``EXPO_PUBLIC_SPREADSHEET_ID``。2026-10-08 に読めることを確認済み）を読み、
  品目を整理して Web 検索で栄養を調べ、方式 A の「結果を貼り付け」欄にそのまま貼れる形式（下記）で渡す。
  件数が多いので、購入回数の多い順に何回かに分ける。
- **方式 A（アプリの窓口。今後の追加分のため）:** 設定画面に「食品データの一括調査」を置く。
  1. 「調査用の文面を作る」: 過去のレシートから未調査の品目（``_foods`` に無い・``pending``・180 日経過）を
     まとめ、調査の指示文と一緒に Android の共有で Gemini / Claude のアプリへ渡す（50 件ずつ。続きは次の回）。
  2. 「結果を貼り付けて取り込む」: AI の答え（下記の形式）を貼ると ``_foods`` に取り込む。
     形式の崩れた行は飛ばして、取り込めた件数・飛ばした件数を出す。
  3. 画面に簡単な手順の説明を載せる（例:「① 文面を作って AI アプリに送る ② AI の答えをまるごとコピーして
     ここに貼る」）。
- **受け渡しの形式:** タブ区切りの表（1 行目に見出し）。列は ``name`` / ``chain`` / ``basis``（piece / package / per100g）/
  ``official``（TRUE / FALSE）/ ``source_url`` / 栄養素のキー（§4 の INFOODS タグ。分からない値は空）。
  指示文で「表だけを返す」「推測した値は official を FALSE」「分からない値は空欄（0 と書かない）」を指定する。

### 8.8.2 よく行くチェーン店のメニューを全部取り込む

- 支出行（店名）と ``_meals`` の店名から、よく行く飲食チェーンを洗い出す（Claude Code がスプレッドシートを読んで調べる）。
- チェーンごとに公式サイトの栄養成分表（多くは PDF で公開）から**全メニュー**を取り込み、``_foods`` に
  ``chain|メニュー名`` の鍵で入れる（basis = package。official = TRUE）。受け渡しは 8.8.1 と同じ形式。
- メニューの改廃があるので、取り込んでから 180 日で調べ直しの対象にする（§3.7 と同じ）。

### 8.8.3 在庫の品目にパッケージ画像を持たせる（v2.3.0 で実装）

- 食品データ（``_foods``）に ``image_url`` 列を足す。栄養を調べたときに grounding が返す参照ページ
  （メーカーの商品ページなど）を読み、ページの代表画像（``og:image``）を取り出して入れる。
- 端末に画像を保存し（``photos/foods/``）、**在庫の一覧と、食事の編集画面の「どれですか？」の選択肢**に表示する。
- 公式ページから取れないときに Google 画像検索で補う案は**見送り**。アプリから Google 画像検索を使う公式の手段は
  件数制限・課金のある API（Custom Search JSON API）に限られ、検索結果のページを直接読み取るのは利用規約に反し、
  仕組みが変わると壊れるため（API の現在の提供状況は着手時に確認する）。取れない品目は画像なしで表示する。必要になったら楽天・Yahoo!ショッピングの
  商品検索 API（無料の開発者登録が必要）で補う案を検討する。

### 8.8.4 圏外で登録したレシートの購入回数を後で記録する

- 今は、レシートの支出行が未送信キューに回ると、その回の購入回数・価格が ``_foods`` に記録されない
  （``recordPurchases`` は読んで足して書く処理なので、追記だけのキューに積めず、通信できないと諦めていた）。
- 記録できなかった品目を端末のファイルに残し、通信が戻ったときの同期（App の ``syncPending``）でまとめて記録する。
- **実装済み（v2.1.1。実機未確認）**: ``recordPurchases`` が失敗したら ``pending-purchases.json`` に積み（最大 200 回分）、
  ``FoodService.flushPendingPurchases`` が未送信キューの再送の後・Gmail 取り込みの前に記録する。記録中に増えた分は残す。

## 11. 1 日ごとの栄養管理（2026-10-08 検討中。未実装）

実機確認（B10・B12）で出た要望から。**1 食単位ではなく、1 日ごとに自分の栄養を管理する**形にする。

### 11.1 決定事項（2026-10-08）

| 項目 | 決定 |
|---|---|
| 食事タブに出す食事 | **自分が食べた食事と、相手と共有された食事だけ**。人の切り替え（チップ）は無くす。合計は自分の分だけ |
| 共有 | **二人で食べた食事は自動で共有**。一人の食事は既定で共有しない。食事の編集画面のチェックで共有にできる。共有しない食事の写真は相手に送らない（`_shared_photos` に載せない）。※スプレッドシート自体は二人で共有しているので、これはアプリ上の見え方の区別 |
| サプリ | 登録したサプリ（1 日の量）を**毎日自動で合計に足す**。飲まなかった日だけ外せる |
| 過不足の判定 | 厚生労働省「日本人の食事摂取基準（2025 年版）」の、年齢・性別・身体活動レベルに応じた値で判定する。「表示」で自分の目標を入れた栄養素はそちらを優先 |

### 11.2 データ（案）

- **プロフィール**: `_nutrition_prefs` に列を足す（生年・性別・身体活動レベル I/II/III）。基準値の年齢区分はアプリで計算する。
- **食事摂取基準**: 公開資料の値をアプリに同梱する（`services/dri2025.ts`。推定平均必要量・推奨量・目安量・目標量・耐容上限量）。
- **共有の印**: `_meals_YYYY-MM` に `shared` 列（TRUE/FALSE）を足す。二人で食べた食事は TRUE で作る。
- **サプリ**: `_supplements`（user / supplement_id / name / nutrients（1 日分）/ per_day / active / note）と、
  飲まなかった日の記録 `_supplement_skips`（user / date / supplement_id）。栄養はパッケージの表示を撮影・入力する
  （公式ページを調べて入れることもできる）。

### 11.3 画面（案）

- 食事タブの既定を「1 日」の画面にする:
  - 上に日付の切り替え。その日の**栄養の表**（栄養素 / 摂取量（食事＋サプリ）/ 基準 / 判定）。判定は色分けした帯
    （不足 = 推奨量・目安量・目標量の下限に届かない / 適正 / 過剰 = 目標量の上限・耐容上限量を超える）。
  - 下にその日の食事の一覧（今の表示）と、その日に足したサプリ（外すスイッチ付き）。
- 「推移」: 栄養素を選んで、直近 7 日・30 日の摂取量を折れ線（基準の帯を重ねる）。週・月の平均の表も出す（今の日・週・月の集計を置き換える）。
- 設定: プロフィール（生年・性別・活動レベル）と、サプリの登録。
